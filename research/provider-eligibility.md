# Additional Agent eligibility

Research for [Research: additional Agents where subscription activation is useful](https://github.com/andreacappadona17/agent-waker/issues/43), checked 2026-10-04. Primary documentation only; no provider commands or subscription requests were run. Recommendations are conditional on the additional Adapter ultimately shipped by [Roadmap: harden the core, then expand reach](https://github.com/andreacappadona17/agent-waker/issues/8): remove that Agent from this shortlist before selecting further targets.

## Finding

**No surveyed candidate yet clears every support gate.** Investigate Kimi Code and Antigravity next, if neither is already the predecessor's new Adapter. Their documented short usage Windows and provider-owned account login make them stronger leads than products with fixed monthly/daily allowances. However, a five-hour limit alone does not establish that a minimal first request starts the whole Window: replenishment could be periodic or consumption-based. That distinction remains unproven for both leads in the sources below.

Z.AI explicitly documents replenishment after consumption, but uses API-key integrations. Qwen's replacement subscription lane also uses a key. A **subscription-backed key is not necessarily pay-as-you-go billing**. Neither product is rejected merely for its key format; both need a support-matrix decision and a provider-owned way to prove the subscription lane without agent-waker reading key material. The present built-in adapters recognize subscription logins and reject their API-key lanes; the core actually gates on `supportsIntent`, rather than unconditionally rejecting an `api_key` enum value ([contract](../src/adapters/contract.ts), [authentication gate](../src/core/orchestrator.ts)).

## Engineering evidence for the two leads

### Kimi Code

- **Authentication / platforms:** account OAuth and Kimi Platform API-key login are separate choices. The current CLI is TypeScript/npm with macOS, Linux, and Windows installation; Windows requires Git Bash. These are native Windows instructions, not a WSL requirement. [Getting started](https://www.kimi.com/code/docs/en/kimi-code-cli/guides/getting-started).
- **Headless / detection:** `-p` and `stream-json` are documented. Print mode automatically handles regular tool calls; static deny rules still apply. `kimi provider list --json` outputs raw provider/model tables, so it must not be assumed safe for authentication inspection without checking whether sensitive fields can appear. Quota-free `--version`/`--help` detection and a nonsecret auth-status interface need captured verification. [Command reference](https://www.kimi.com/code/docs/en/kimi-code-cli/reference/kimi-command.html).
- **Containment:** an explicit agent file can select a main agent with `tools: []`; tool boundaries are enforced before execution. This is a promising tool-free interaction surface. Inherited instructions, hooks/plugins, and auxiliary requests still require verification with the exact supported release. [Agent files](https://www.kimi.com/code/docs/en/kimi-code-cli/customization/agents.html).
- **Blocks / billing:** documented five-hour and weekly exhaustion are HTTP 403, as are some permission failures: never classify every 403 as quota. The example five-hour message states no absolute reset; a Console reset is not automatically a CLI Observation. Monthly shared credits add another independently limiting pool. Whether purchased Extra Usage is automatically consumed, and how to refuse it per invocation, remains unresolved. [Error reference](https://www.kimi.com/code/docs/en/kimi-code/error-reference.html), [membership credit rules](https://www.kimi.ai/help/membership/update-rules).
- **Maintenance assessment:** medium/high until version boundaries are pinned. The provider documents a Python-to-TypeScript rewrite with incompatible configuration and a print-mode false-success fix; do not transplant legacy CLI fixtures or rely on exit zero alone. [Release history](https://www.kimi.com/code/docs/en/kimi-code/whats-new.html), [CLI changelog](https://www.kimi.com/code/docs/en/kimi-code-cli/changelog.html).

### Antigravity

- **Authentication / platforms:** native macOS/Linux/Windows and provider-owned OS-keyring login are documented. A separate API-key provider mode exists; simply removing `GEMINI_API_KEY` does not establish the account lane if that provider mode remains configured. A nonsecret account/plan status command suitable for scheduled inspection remains unverified. [Install and authentication](https://www.antigravity.google/docs/cli/install/).
- **Headless / containment:** `agy -p`, JSON/NDJSON, terminal states, and bounded print timeout are documented; unauthenticated headless runs error instead of prompting. Sandbox and deny rules exist, but sandboxing alone does not disable all tools or inherited hooks/MCP. Prove a per-run containment configuration and fail-closed behavior rather than assuming a prompt is protection. [Headless](https://www.antigravity.google/docs/cli/headless/), [CLI permissions](https://www.antigravity.google/docs/permissions?tab=cli).
- **Billing refusal:** the CLI documents `useG1Credits` and a setting to disable credit fallback. This is a useful control, not proof that agent-waker can safely enforce it without editing a user's global configuration. Verify per-run override and effective setting before activation. [CLI credits](https://www.antigravity.google/docs/cli/credits/).
- **Probes / reset evidence:** `/usage` is an interactive quota panel, not a documented headless machine-readable probe. Do not submit it as an ordinary `-p` prompt. Contributor reports in the provider-owned issue tracker show relative reset messages and headless in-process retries, useful leads for fixture capture but not a stable protocol guarantee. [Usage command](https://antigravity.google/docs/cli/commands/usage), [reported retry behavior](https://github.com/google-antigravity/antigravity-cli/issues/1018). Shell `--help`/`--version` smoke checks need captured verification.
- **Maintenance assessment:** medium/high: model-specific pools, relative resets, provider retries, keyring behavior, and configurable overages all affect the contract. Use a small supported version range until captured behavior is demonstrated; native Windows availability alone is not scheduler-session authentication evidence.

## Revalidation and limits

The earlier [Research: candidate provider CLIs’ block/reset signals](https://github.com/andreacappadona17/agent-waker/issues/25) is context, not authority. Its asserted Gemini consumer cutoff and successor relationship have no traceable source in the supplied resolution. Current Gemini documentation still describes individual/free and Pro/Ultra daily lanes; Antigravity is independently documented. Neither establishes the claimed cutoff or migration. Preserve this uncertainty rather than repeating the claim. [Gemini quotas](https://geminicli.com/docs/resources/quota-and-pricing/), [Antigravity authentication](https://www.antigravity.google/docs/cli/install/).

OpenCode is a multi-provider client, so assess an exact subscription/provider lane rather than treating another frontend as a new allowance. Its provider integrations are evidence to investigate, not permission to bypass the selected provider's auth or billing constraints. [Providers](https://opencode.ai/docs/providers/).

Ineligible fixed-allowance candidates were stopped at the benefit gate; full CLI/platform/containment audits would not alter that decision. This is a bounded shortlist, not an exhaustive catalogue or promise of eligibility. No new-provider fixtures exist in this checkout's [captured fixtures](../test/fixtures); public docs are not fabricated runtime fixtures.

## Evidence required before implementation

For each selected lead, obtain a volunteer subscription user and exact provider/version/OS/model lane. The human authenticates using the provider; agent-waker never opens credential files or exports secrets.

1. Establish whether idle-to-first-request changes the relevant reset. Prefer provider documentation/support confirmation or voluntary evidence from ordinary usage; do not spend requests solely for measurement. Distinguish whole-window activation from per-consumption replenishment and fixed calendar refreshes.
2. Establish provider-owned nonsecret auth introspection and a fail-closed invocation that refuses PAYG, alternate endpoints/providers, and purchased-credit fallback. If unavailable, selection remains conditional.
3. Capture sanitized version/help/auth-status, successful minimal interaction, exhausted short/weekly quota, login expiry, permission/model entitlement denial, network failure, malformed output, and timeout from naturally occurring or human-authorized use. Record stdout, stderr, exit status, timezone and version; never publish credential-bearing raw tables or sessions.
4. Demonstrate tool/MCP/hook containment with fake executables and fixtures. Validate real provider behavior manually through the support decision, including Windows keyring/session availability if native Windows is selected.
5. Declare exact-reset and weekly-limit capabilities only from verified observations. Relative or ambiguous reset text must not become a trusted absolute timestamp by guesswork; follow [ADR 0001](../docs/adr/0001-adapters-report-facts-core-decides.md) and [ADR 0002](../docs/adr/0002-auth-and-install-problems-never-enter-quota-backoff.md).

The research resolves the shortlist and its unknowns. It does not select an Agent, revise the authentication contract, or authorize implementation; those belong to the linked support-matrix decision.
